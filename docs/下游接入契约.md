# Kalm 下游接入契约

> 面向前端 / 下游厂商接入方的协议、通知、状态码总览。
> 核心原则：**透明代理 + FIFO 排队**。后端用什么协议，Kalm 对前端就暴露什么协议。

---

## 1. 四条交互通道总览

| 通道 | 端点 | 用途 | 协议 |
|---|---|---|---|
| 任务提交 | `POST /interface/tasks/submit` | 提交任务、拿 `task_id` + `track_mode` | HTTP + 信封 |
| 状态查询 | `GET /interface/tasks/{id}/status` | 轮询任务结果 | HTTP + 信封 |
| 单任务进度 | `WS /interface/tasks/{id}/ws` | 实时进度推送 | WebSocket |
| 队列广播 | `WS /interface/queue/ws` | 任务生命周期通知 | WebSocket |
| 流式输出 | `POST /interface/llm/generate-stream` / `GET /interface/tasks/{id}/stream` | 云端大模型逐 Token | NDJSON 流 |
| 全方法透明代理 | `ANY /proxy/{service_name}/{path:path}` | 透传非算力管理/试听/文件下载接口 | HTTP 透明流 |

> 💡 **TTS 配音、情绪控制、音色/情绪管理、试听鉴权与 `/proxy/tts/...` 完整接入指南**：请参阅 [TTS与透明代理服务前端接入指南.md](file:///d:/AIGC/KamlPro/docs/TTS与透明代理服务前端接入指南.md)。

## 2. 认证契约

由 `config.yaml` 的 `api_server.tokens` 驱动，**留空则完全免认证**。

**HTTP**：`Authorization: Bearer <token>` 头。

**WebSocket**（三种 token 传递方式，任一命中即可）：
1. `Authorization: Bearer <token>`
2. `x-token: <token>`
3. `Sec-WebSocket-Protocol: kalm-auth, <token>`（浏览器场景，握手会回传 subprotocol）

**认证失败反馈（下游必须能区分）**：

| 场景 | 状态码 / 关闭码 |
|---|---|
| HTTP 无 `Authorization` 头 | **403** `{"detail":"Not authenticated"}` |
| HTTP token 无效 | **401** `{"detail":"Invalid authentication token"}` |
| WS 连 Kalm 路径但 token 无效 | **关闭码 4001** `"Missing or invalid authentication token"` |
| WS 连非 Kalm 路径（如 `/ws`） | **关闭码 1000**（静默） |

---

## 3. HTTP 通用信封 + 状态码

所有业务 HTTP 接口（除流式/文件/静态外）统一信封：

```json
{ "status": "success" | "error", "message": "ok" | "...", "data": <任意> | null }
```

**下游会遇到的 HTTP 状态码全集**：

| 码 | 语义 | 典型 message |
|---|---|---|
| 200 | 成功 | `"ok"` / `"Task cancellation initiated"` / `"Task is already finished"` |
| 400 | 请求参数错误 | `Missing 'task_type'...` / `Unknown task type: '...'` / `Request body must be valid JSON...` |
| 401 | token 无效 | `Invalid authentication token` |
| 403 | 缺 Authorization 头 | `Not authenticated` |
| 404 | 资源不存在 | `Task '<id>' not found` / `Stream not found or expired` / `Service '<name>' not found` |
| 500 | 内部错误 | `Failed to submit task: ...` / `Proxy error: ...` |
| 502 | 后端不可达 | `Backend service '<name>' is not reachable` |
| 503 | 排队超时/过载 | `Task queue timeout — service busy, retry later` |

## 4. 任务状态机

| 值 | 含义 |
|---|---|
| `pending` | 已创建，尚未入队 |
| `queued` | 已入 FIFO 队列等待 |
| `running` | 执行中 |
| `success` | 成功（`result` 有产物） |
| `failed` | 失败或被取消（`result.message` 有原因） |
| `not_found` | 任务不存在（`GET /status` 会转成 **404**） |

> 提交任务时响应里的 `data.status` 只可能是 **`queued`** 或 **`running`**（云端闲时直连）两种。

---

## 5. track_mode 路由决策

提交后根据响应里的 `track_mode` 决定后续怎么跟进度：

| track_mode | 下游动作 |
|---|---|
| `ws` | 连 `WS /interface/tasks/{id}/ws` 收进度 |
| `poll` | 轮询 `GET /interface/tasks/{id}/status` |
| `stream` | 连 `GET /interface/tasks/{id}/stream` 拉 NDJSON 流 |

当前 `configs/tasks.yaml` 实际映射：`comfyui / llm / tts / subtitle → ws`，`llm_streaming → stream`。即**本地任务全部收敛到 `ws`**（双轨制统一 WS 推送），只有云端流式走 `stream`。

> 响应还带 `hint` 字段，直接告诉下游该连哪个地址。

## 6. WS 单任务频道消息契约（`/tasks/{id}/ws`）

**连接建立瞬间**，Kalm 先根据任务当前状态发一帧：

| 任务状态 | 首帧 |
|---|---|
| 不存在 | `{"type":"error","message":"Task not found"}` → 关闭 |
| 已 success | `{"type":"task_complete","status":"success","result":{...}}` → 关闭 |
| 已 failed | `{"type":"task_complete","status":"failed","result":{...}}` → 关闭 |
| 进行中 | 保持连接，进入实时推送 |

**进行中的实时消息类型**（下游需处理的 `type` 全集）：

| type | 来源 | 载荷要点 |
|---|---|---|
| `task_running` | 调度器（云端排队转执行） | `status`,`task_id` |
| `queued` | ComfyUI | `status`,`prompt_id` |
| `progress` | ComfyUI 原生透传 | `data.value`,`data.max` |
| `executing` / `executed` / `execution_start` / `execution_cached` | ComfyUI 原生透传 | `data.node` 等 |
| `overall_progress` | **平滑拦截器合成（推荐绑定）** | `data.percent`(0-99 单调递增),`data.message` |
| `awaiting_delivery` | ComfyUI | `status:"completed"`,`prompt_id`,`output_nodes` |
| `execution_error` | ComfyUI | `data`（随后任务转 failed） |
| TTS/字幕后端 `status_data` | IndexTTS 透传 | 含后端 `status` 字段 |
| `task_complete` | 终态 | `status:"success"`,`result`/`outputs` |
| `task_failed` | 终态 | `message` |

**兜底**：即使 executor 主线不推，`poll_fallback` 每 2s 轮询一次，任务终态时补发 `task_complete`/`task_failed`。

## 7. WS 全局单轨总线（`/interface/queue/ws`）与队列大盘

> 🌟 **商业级全局单轨架构**：下游强烈推荐采用**单轨全托管模式**。接入方在整个前端生命周期中**仅需维持这一条长连接**，即可获取全局大盘水位、排队实时排位、JIT 素材上传吹哨、300ms 智能节流进度以及最终产物成果，**彻底淘汰繁琐易漏的单个任务独立 WS 频道**！

---

### 7.1 连接与身份绑定（`client_id` 机制）

* **连接端点**：`ws://{host}:{port}/interface/queue/ws?client_id={my_client_id}`
* **鉴权方式**（支持以下任一方式）：
  1. Header：`Authorization: Bearer <token>`
  2. Header：`x-token: <token>`
  3. 子协议（浏览器原生 WS 场景）：`Sec-WebSocket-Protocol: kalm-auth, <token>`
* **多租户数据隔离**：
  - 建立 WS 连接与调用 `POST /interface/tasks/submit` 提交任务时，必须携带一致的 `client_id`；
  - 服务端根据 `client_id` 进行连接池物理隔离，进度及结果**精准定向推送**给所属客户端，彻底杜绝数据串台；
  - **强校验原则（Fail-Fast 拒绝兜底）**：严禁缺省 `client_id`！若未传 `client_id`，WS 握手直接被拒绝（Code 1008，`Policy Violation`），HTTP 任务提交直接返回 400 拦截中断，全系统坚决不做任何全网广播或匿名兜底。
* **心跳保活**：客户端建议每 30 秒发送文本 `"ping"`，服务端立即回复文本 `"pong"`。

---

### 7.2 下发消息与状态全集（9 种消息类型 + 1 种心跳）

| 序号 | 消息类型 (`type`) | 触发阶段 / 时机 | 核心作用与说明 |
|:---:|---|---|---|
| 1 | `queue_snapshot` | **WS 握手成功首帧** | 立即同步全局队列水位、GPU 忙闲状态、当前运行服务及属于该客户端的全部历史/活跃任务列表。 |
| 2 | `task_enqueued` | **任务提交成功入队** | 通知任务进入 FIFO 调度队列，包含排队顺位（第几位）、队列总深度、资产就绪状态。 |
| 3 | `task_asset_required` | **轮到该任务（JIT吹哨）** | 若提交时声明延迟上传资产（`asset_status: "not_ready"`），出队前向客户端吹哨索要素材并开启 30 秒开闸等待。 |
| 4 | `task_started` | **任务开始执行起跑** | 任务正式出队，本地 GPU 开始推理或云端并发 API 开始调用。 |
| 5 | `task_progress` | **推理计算进行中** | 经服务端 **300ms 智能节流** 聚合后的计算进度百分比（0~99）及阶段描述。 |
| 6 | `task_completed` (成功) | **任务成功完成** | 任务执行成功终态，包含最终产物路径/结果对象，打满 100% 进度，并告知下一顺位任务信息。 |
| 7 | `task_completed` (失败) / `task_failed` | **任务失败 / 取消 / 连坐清理** | 任务异常、用户手动取消或因超时/失联被连坐清理，携带明确失败原因。 |
| 8 | `queue_positions_updated` | **顺位动态流转（动作A/B/C）** | **高频轻量顺位映射** `{ [task_id]: position }`。前方任务起跑、完成或取消出队时高频广播，驱动排队位次实时递减。 |
| 9 | `task_cancelled` | **用户手动取消出队** | 任务被调用 `cancel` 接口主动停止时发出，与 `task_failed` 并发推送。 |
| 10 | `pong` | **心跳回应** | 响应客户端发送的 `"ping"` 心跳包，维持连接活跃。 |

### 7.3 全状态数据报文样例与字段详解

#### 状态 1: `queue_snapshot`（连接首帧快照）

* **触发时机**：客户端与 WebSocket 握手成功建立连接的**第 1 帧**，服务端主动立即下发。
* **数据结构样例**：
```json
{
  "type": "queue_snapshot",
  "data": {
    "client_id": "client_alpha_888",
    "total_queued": 3,
    "is_busy": true,
    "current_running_service": "ComfyUI",
    "active_cloud_tasks": 0,
    "queue_list": [
      {
        "position": 1,
        "task_id": "8f12d8a0-2101-443b-a2c1-d41987d60e51",
        "task_type": "comfyui",
        "client_id": "client_alpha_888"
      },
      {
        "position": 2,
        "task_id": "e429bb11-4039-4412-9c12-ef871239ab76",
        "task_type": "comfyui",
        "client_id": "client_alpha_888"
      }
    ],
    "your_tasks": {
      "8f12d8a0-2101-443b-a2c1-d41987d60e51": {
        "status": "queued",
        "task_type": "comfyui",
        "client_id": "client_alpha_888",
        "asset_status": "ready",
        "required_assets": [],
        "created_at": 1773225890.12,
        "result": {}
      },
      "7d312984-ffaa-4567-bcde-998877665544": {
        "status": "success",
        "task_type": "comfyui",
        "client_id": "client_alpha_888",
        "asset_status": "ready",
        "required_assets": [],
        "created_at": 1773225800.55,
        "result": {
          "images": [
            {
              "filename": "ComfyUI_00012_.png",
              "subfolder": "",
              "type": "output",
              "url": "http://127.0.0.1:7000/interface/files/ComfyUI_00012_.png"
            }
          ]
        }
      }
    }
  }
}
```
* **字段说明**：
  * `total_queued`: 全局当前排队任务总数（含其他客户端）。
  * `is_busy`: 当前 GPU 是否正在忙碌（`true` 表示 GPU 正在执行任务）。
  * `current_running_service`: 当前常驻占用 GPU 的服务名称（如 `"ComfyUI"`、`"TTS"`，空闲时为 `null`）。
  * `active_cloud_tasks`: 当前正在执行的云端并发任务数量。
  * `queue_list`: 属于该 `client_id` 当前在队列中的工单列表，含实时 `position`（顺位）。
  * `your_tasks`: 属于该 `client_id` 的全部任务（排队中、执行中、已完成、已失败）的深拷贝映射。
* **前端处理建议**：
  * 页面刷新或初次加载时，根据 `queue_snapshot` 直接恢复历史任务列表与当前排队 UI，无需再发多次 HTTP 轮询。

#### 状态 2: `task_enqueued`（任务入队通知）

* **触发时机**：调用 `POST /interface/tasks/submit` 成功后，任务被推入 FIFO 队列的瞬间。
* **数据结构样例**：
```json
{
  "type": "task_enqueued",
  "task_id": "8f12d8a0-2101-443b-a2c1-d41987d60e51",
  "task_type": "comfyui",
  "client_id": "client_alpha_888",
  "track_mode": "ws",
  "queue_position": 2,
  "total_queued": 2,
  "asset_status": "ready",
  "message": "任务已排入队列，前方排队 1 人"
}
```
* **字段说明**：
  * `queue_position`: 该任务在当前队列中的排位序号（1 表示马上执行；云端任务直接并发运行，固定为 0）。
  * `total_queued`: 包含该任务在内的队列总深度。
  * `asset_status`: 资产就绪状态（`"ready"` 表示无需补传直接排队；`"not_ready"` 表示等待调度吹哨）。
* **前端处理建议**：
  * 在 UI 上渲染“排队中”标签，并显示“前方排队 X 人”，将该任务加入等待列表。

---

#### 状态 3: `task_asset_required`（JIT 延迟素材上传吹哨）

* **触发时机**：该任务提交时标记了 `asset_status: "not_ready"`，在排到队伍第一位即将送入 GPU 时触发。
* **数据结构样例**：
```json
{
  "type": "task_asset_required",
  "task_id": "8f12d8a0-2101-443b-a2c1-d41987d60e51",
  "task_type": "subtitle",
  "client_id": "client_alpha_888",
  "track_mode": "ws",
  "required_assets": ["audio"],
  "upload_url": "/interface/tasks/8f12d8a0-2101-443b-a2c1-d41987d60e51/assets",
  "timeout": 30,
  "message": "轮到您的任务了！请在30秒内上传素材文件以开闸运行"
}
```
* **字段说明**：
  * `required_assets`: 声明需要补传的文件字段数组（如 `["audio"]` 或 `["image"]`）。
  * `upload_url`: 专属文件上传 HTTP 路径，客户端直接将文件 `POST` 至此地址。
  * `timeout`: 客户端响应超时的倒计时秒数（默认 30 秒）。
* **前端处理建议**：
  * 监听到该事件后，前端无需用户再次干预，自动从前端待传池或文件缓存中调用 `upload_url` 触发 `multipart/form-data` 上传；
  * UI 上可显示“正在向 GPU 上传大文件素材...”。

---

#### 状态 4: `task_started`（任务出队起跑）

* **触发时机**：素材已就绪，GPU 资源就绪，调度器正式将任务交付给执行器执行的瞬间。
* **数据结构样例**：
```json
{
  "type": "task_started",
  "task_id": "8f12d8a0-2101-443b-a2c1-d41987d60e51",
  "task_type": "comfyui",
  "client_id": "client_alpha_888",
  "track_mode": "ws",
  "message": "本地 GPU 任务开始执行"
}
```
* **前端处理建议**：
  * 将任务状态由“排队中/上传中”切换为“生成中”；
  * 初始化进度条为 0%，准备接收 `task_progress` 进度驱动。

---

#### 状态 5: `task_progress`（实时计算进度推送）

* **触发时机**：执行器在模型推理计算期间持续产生进度，服务端经 **300ms 智能节流窗口**平滑聚合后下发。
* **数据结构样例（图片生成场景 - ComfyUI）**：
```json
{
  "type": "task_progress",
  "task_id": "8f12d8a0-2101-443b-a2c1-d41987d60e51",
  "client_id": "client_alpha_888",
  "progress": 64.5,
  "message": "采样中 (13/20 步) - KSampler",
  "node_name": "KSampler"
}
```
* **数据结构样例（语音合成场景 - TTS）**：
```json
{
  "type": "task_progress",
  "task_id": "e429bb11-4039-4412-9c12-ef871239ab76",
  "client_id": "client_alpha_888",
  "progress": 50.0,
  "message": "正在合成文本分段 (2/4)"
}
```
* **字段说明**：
  * `progress`: 浮点数或整数，取值范围 `0 ~ 99`（单调递增，不跳步回退）。
  * `message`: 当前阶段的人类可读中文描述。
  * `node_name`: 当前正在计算的底层工作流节点名称（可选）。
* **前端处理建议**：
  * 直接以 `msg.progress` 更新进度条宽度，以 `msg.message` 刷新进度文案提示。

---

#### 状态 6: `task_completed` - 成功（任务执行完成终态）

* **触发时机**：任务所有节点计算完毕，产出物落盘完成。
* **数据结构样例（ComfyUI 图片生成）**：
```json
{
  "type": "task_completed",
  "task_id": "8f12d8a0-2101-443b-a2c1-d41987d60e51",
  "task_type": "comfyui",
  "client_id": "client_alpha_888",
  "status": "success",
  "result": {
    "images": [
      {
        "filename": "ComfyUI_00012_.png",
        "subfolder": "",
        "type": "output",
        "url": "http://127.0.0.1:7000/interface/files/ComfyUI_00012_.png"
      }
    ],
    "duration": 4.82
  },
  "next_task_id": "e429bb11-4039-4412-9c12-ef871239ab76",
  "next_task_type": "comfyui",
  "next_track_mode": "ws",
  "message": "本地 GPU 任务执行完成"
}
```
* **数据结构样例（TTS 语音合成）**：
```json
{
  "type": "task_completed",
  "task_id": "e429bb11-4039-4412-9c12-ef871239ab76",
  "task_type": "tts",
  "client_id": "client_alpha_888",
  "status": "success",
  "result": {
    "audio_url": "http://127.0.0.1:7000/interface/files/tts_output_e429.wav",
    "duration": 3.12
  },
  "next_task_id": null,
  "next_task_type": null,
  "next_track_mode": null,
  "message": "本地 GPU 任务执行完成"
}
```
* **字段说明**：
  * `status`: 固定为 `"success"`。
  * `result`: 产物具体数据（直接包含图片、音频或文本输出的完整结构）。
  * `next_task_id`: 队列中紧排在该任务之后的下一个任务 ID（若无后继任务则为 `null`）。
  * `next_task_type`: 下一个任务类型，方便前端预先获知。
* **前端处理建议**：
  * 进度条打满 100%；
  * 直接读取 `result` 中的图片或音频地址进行界面渲染展示；
  * 若有 `next_task_id`，可在界面上将下一任务预热为准备起跑。

---

#### 状态 7: `task_completed` - 失败 / 取消 / 连坐清理（终态异常）

* **触发时机**：
  1. 任务推理内部错误（如显存不足 OOM、工作流配置缺失）；
  2. 客户端调用 `POST /tasks/{id}/cancel` 主动取消；
  3. **连坐清理机制**：吹哨后 30 秒超时无响应，或客户端断开 WS 超过 30 秒，服务端自动连坐取消名下排队任务。
* **数据结构样例（用户手动取消场景）**：
```json
{
  "type": "task_completed",
  "task_id": "8f12d8a0-2101-443b-a2c1-d41987d60e51",
  "task_type": "comfyui",
```

#### 状态 8: `queue_positions_updated`（专职轻量顺位流转广播）

* **优化背景与精简原则**：
  在 FIFO 队列物理模型中，队伍中各任务的顺位仅在**有任务离开待执行队列**时才会发生实质性前移。为避免无效广播与客户端频繁空转，本事件已收敛精简，**有且仅在以下两处核心时机触发**：
* **保留的触发时机（有且仅此两处实质出队动作）**：
  1. **【核心主干】调度器出队起跑/吹哨时（Pop 送 GPU 瞬间）**：
     调度器从待执行队列头部取出任务的那一瞬间（即下发 `task_started` 或 JIT `task_asset_required` 时），有且仅向客户端广播 1 次 `queue_positions_updated`，同步所有剩余排队任务顺位前移；
  2. **【唯一特例】排队中任务被用户主动取消时（Cancel while Queued）**：
     客户端调用 `/cancel` 接口且目标任务仍在队列中等待时，从队列中移出该任务并广播 1 次 `queue_positions_updated`；
  3. *(冷启动握手补位)*：客户端与 WebSocket 握手连上首帧后补发 1 次当前顺位字典，供前端冷启动即时校准。
* **彻底移除的冗余触发点（杜绝重复报文刷屏）**：
  * ❌ 移除 `task_completed` 处的广播：任务出队起跑时其顺位早已前移结算完毕，任务执行完毕出产物时队列结构没有任何变动；
  * ❌ 移除 `task_failed` 处的广播：执行中失败同样不影响等待中的排队任务；
  * ❌ 移除 `task_enqueued` 处的全局顺位广播：新任务永远追加在队尾，前面的所有排队任务顺位完全不受影响；新任务的排位仅需在该任务专属的 `task_enqueued` 报文中携带，无需全局多余广播。
* **数据结构样例（纯键值字典映射）**：
```json
{
  "type": "queue_positions_updated",
  "data": {
    "3b490a68-c2ae-4aa6-9dde-e06dbd356b46": 1,
    "8f12d8a0-2101-443b-a2c1-d41987d60e51": 2,
    "e429bb11-4039-4412-9c12-ef871239ab76": 3
  }
}
```
* **字段说明**：
  * `data`: `{ [task_id]: position }` 纯键值映射字典。
    * `task_id`: 处于排队等待中的任务 ID；
    * `position`: 1-based 整数（`1` 表示排在队伍第 1 位即将开始执行；`2` 表示前方还有 1 人；`3` 表示前方还有 2 人...以此类推）；
    * 当队列中无任何排队等待中的任务时，`data` 为空字典 `{}`。
  * **多租户隔离**：若客户端连接携带了 `client_id`，服务端在保持全局真实物理顺位的同时，仅下发归属于该 `client_id` 的任务映射，杜绝数据越权。
* **前端处理建议**：
  * 监听到该事件后，前端直接通过 `const pos = msg.data[taskId]` 实时刷新对应任务卡片的排队序号（`pos === 1 ? "即将出队执行" : "前方排队 " + (pos - 1) + " 人"`）；
  * 若任务已出队不在 `msg.data` 中，其在收到 `task_started` 时将自然切换至执行中态，队伍序号实现完美动态递减！

### 7.5 前端极简接入代码范式（TypeScript / JavaScript）

```typescript
// 1. 初始化建立全局单轨 WebSocket 连接
const clientId = "client_alpha_888";
const token = "123456";
const wsUrl = `ws://127.0.0.1:7000/interface/queue/ws?client_id=${clientId}`;

const ws = new WebSocket(wsUrl, ["kalm-auth", token]);

// 2. 维持心跳
setInterval(() => {
  if (ws.readyState === WebSocket.OPEN) {
    ws.send("ping");
  }
}, 30000);

// 3. 统一分发消息调度器
ws.onmessage = async (event) => {
  if (event.data === "pong") return; // 心跳应答

  const packet = JSON.parse(event.data);
  const { type, task_id } = packet;

  switch (type) {
    case "queue_snapshot":
      // 握手首帧：渲染大盘水位与当前全部任务
      renderQueueSnapshot(packet.data);
      break;

    case "task_enqueued":
      // 入队通报：更新排队顺位
      updateTaskQueueBadge(task_id, packet.queue_position);
      break;

    case "task_asset_required":
      // JIT 吹哨：自动补传素材开闸放行
      await uploadTaskAssets(task_id, packet.upload_url, packet.required_assets);
      break;

    case "task_started":
      // 起跑通报：初始化进度条
      setTaskRunning(task_id);
      break;

    case "task_progress":
      // 实时进度（300ms 平滑节流）：驱动进度条与提示文本
      updateTaskProgressBar(task_id, packet.progress, packet.message);
      break;

    case "task_completed":
      if (packet.status === "success") {
        // 完成：进度打满 100%，渲染结果图片/音频
        renderTaskSuccess(task_id, packet.result);
      } else {
        // 失败或取消：展示失败原因
        renderTaskFailure(task_id, packet.result?.message);
      }
      break;
  }
};
```

## 9. 取消语义

`POST /interface/tasks/{id}/cancel` 后：

- 返回 **200**（`Task cancellation initiated`），或任务已结束时 **200**（`Task is already finished`）。
- 任务最终 `status` 会落为 **`failed`**，且 `result.message = "任务已被用户手动停止"`。
- 双频道都会收到 `task_failed`（单任务频道 + 队列广播各一次，**下游需去重**）。

## 10. 边界点与注意事项

1. **终态双份通知**：完成/失败时，单任务频道与队列广播会各推一次，务必按 `task_id` + `type` 去重。
2. **任务 TTL**：`success/failed` 任务默认 1 小时后被清理，届时 `GET /status` 变 404，产物目录也会被定时清理。
3. **`overall_progress` 优先**：ComfyUI 复杂工作流进度会回跳，下游应优先绑定 `overall_progress`（单调递增 0-99），其余原生事件仅作参考/日志。
4. **LLM 本地 vs 云端**：本地 Ollama 只能非流式（`track_mode=ws`）；云端才走 `stream`。提交时若为云端且闲时，`data.status` 会直接是 `running` 并附 `can_stream_immediately`。
5. **WS 认证关闭码**：连接被 `4001` 关闭 = 鉴权失败（不是业务错误），`1000` = 非 Kalm 路径。
6. **`GET /interface/tasks`（任务列表）** 返回 `data.tasks` 为任务 id → 任务字典的映射快照（不含任务详情语义，仅用于自检/调试）。

## 11. 队列排队调度与显存优化（批量与追加契约）

1. **允许任意时刻动态追加任务**：接入方无需等待前序任务执行完毕，可随时连续调用 `POST /interface/tasks/submit` 追加任务至队列。
2. **同类型任务追加（如 ComfyUI → ComfyUI）**：前序任务完成时，调度器窥探到同类型后继任务，**跳过释放** (`skip free`)，大模型常驻显存，零重载极速复用。
3. **异构任务追加（如 ComfyUI → TTS）**：前序任务完成时，调度器窥探到类型切换，**自动调用 `free_api` 释放旧显存**，并平滑切换拉起新服务，彻底杜绝单卡 OOM 崩溃。
4. **全自动闭环**：显存释放由网关调度器自适应管控，接入方完全无需干预。

| 队列状态 | 行为 | 效果 |
|---|---|---|
| **队列中有同类型任务** | **跳过释放** (`skip free`) | 模型常驻显存，极速复用，无需重载 |
| **队列中有不同类型任务** | **释放显存** | 卸载旧模型，为新服务让渡显存 |
| **队列为空** | **释放显存** | 闲置时回收 GPU 资源 |

> ⚠️ **接入方重要实践**：
> - 释放决策基于当前**已排队**的任务。若接入方采取“等前一个任务跑完再发下一个”的串行提交模式，每次完成时队列为空，必然触发模型卸载并导致下一次任务产生昂贵的重载开销。
> - **强烈推荐批量连续入队或提早追加**：配合 `WS /interface/queue/ws` 队列广播按序收割结果。
> - 详细技术规格请参阅独立交付文档：[任务队列机制与资源调度接入交付指南.md](file:///d:/AIGC/KamlPro/docs/任务队列机制与资源调度接入交付指南.md)。

### 12.5 防误杀 Watchdog 与连坐清理 (Purge) 机制
1. **传输防误杀机制**：
   * 30 秒超时仅为“吹哨发起超时”，一旦客户端发起 HTTP 上传请求，任务状态立即切入 `asset_uploading`。
   * 大文件传输期间，系统提供长达 300 秒的流式传输宽限，绝不因文件体量过大被误杀。
2. **超时连坐清理**：
   * 若吹哨 30 秒内客户端完全未响应，判定该任务超时失联；
   * 触发**连坐清理机制**（Purge）：立即将该 `client_id` 名下**所有排队与等待中的任务**批量置为 `failed` 并移出队列；
   * 调度器立刻跳过该客户端任务，调度后续其他客户端的任务，彻底避免断线用户占用宝贵的 GPU 算力。
3. **断线离线监测**：
   * 调度器在任务出队时会检查对应 `client_id` 的离线时长。若断开 WS 超过 30 秒，自动连坐清理该客户端全部排队任务。
